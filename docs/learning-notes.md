# 学習メモ

## データ構造の設計

- 保存するデータと、コンポーネントの状態管理は別で考える。
- データ構造を設計する上で、状態管理が必要な部分は考慮に入れず、コンポーネント設計に委ねる。
- 同じデータを複数の場所で持たずIDによる参照を利用する。
- すべての値をデータで保存するのではなく、計算から算出できるものは計算する。
- 保存するデータと一時的に使用するデータはStorageに保存すべきかを考える。
- データごとに責任範囲を明確にし、どのデータをどこで管理するかを決める。
- データ同士の関係性を整理し、どのデータを基準に取得・更新するかを明確にする。
- どのデータがその情報の保有者なのかを明確にし、管理する場所と利用する場所を分ける。
- 同じデータを複数の箇所で保存しない。1か所で管理しデータの受け渡しをする。
- カレンダーのような表として扱うデータは、自身にデータを持たせない。
- UIの一時的な状態はデータ構造に入れない。コンポーネント設計の役割。
-

##　コンポーネント設計

- コンポーネントの責務を明確にする。状態をどのコンポーネントが持つ可能性があるかを考慮する。
- コンポーネントは親子関係から決めていく、最初からデータの流れを追わない。
- 親子関係は、そのコンポーネントを構成する要素を考える。
- 重複するコンポーネントは最後にcommonsとして整理していく。初めは重複は気にせず、コンポーネントの構成を優先する。
- あくまでコンポーネントとして成立するくくりにしておくこと。HTMLの要素は実装時で問題ない。
- コンポーネントは、役割と構成要素に絞って置き、データの関係性や状態の詳細については実装時に考える。ただし、設計段階でも状態管理が必要になる可能性は考慮する。具体的な状態の変化は実装時に決定する。
- 関数で書けるものはコンポーネントとして成立するとはかぎらない。UIとして表示するまとまりであるかを考える。
- 設計段階では、実装時の判断までを考慮するのは難しいため、コンポーネントとして候補に挙がる境界線を意識する程度で問題ない。
- コンポーネントはデータを扱うが、保存状況に関わらず状態管理は行われる。セレクトボックスのように状態変化はあるがデータを保存しないこともある。
- 毎回同じ時間設定をするなど、データとして保存されることもある。
- 状態管理の実装方法は、コンポーネント設計の段階では確定できない。状態管理の可能性を優先的に考慮する。
