# 学習メモ

## データ構造の設計

- 保存するデータと、コンポーネントの状態管理は別で考える。
- データ構造を設計する上で、状態管理が必要な部分は考慮に入れず、コンポーネント設計に委ねる。
- 同じデータを複数の場所で持たずIDによる参照を利用する。
- すべての値をデータで保存するのではなく、計算から算出できるものは計算する。
- 保存するデータと一時的に使用するデータはStorageに保存すべきかを考える。
- データごとに責任範囲を明確にし、どのデータをどこで管理するかを決める。
- データ同士の関係性を整理し、どのデータを基準に取得・更新するかを明確にする。
- どのデータがその情報の保有者なのかを明確にし、管理する場所と利用する場所を分ける。
- 同じデータを複数の箇所で保存しない。1か所で管理しデータの受け渡しをする。
- カレンダーのような表として扱うデータは、自身にデータを持たせない。
- UIの一時的な状態はデータ構造に入れない。コンポーネント設計の役割。

##　コンポーネント設計

- コンポーネントの責務を明確にする。状態をどのコンポーネントが持つ可能性があるかを考慮する。
- コンポーネントは親子関係から決めていく、最初からデータの流れを追わない。
- 親子関係は、そのコンポーネントを構成する要素を考える。
- 重複するコンポーネントは最後にcommonsとして整理していく。初めは重複は気にせず、コンポーネントの構成を優先する。
- あくまでコンポーネントとして成立するくくりにしておくこと。HTMLの要素は実装時で問題ない。
- コンポーネントは、役割と構成要素に絞って置き、データの関係性や状態の詳細については実装時に考える。ただし、設計段階でも状態管理が必要になる可能性は考慮する。具体的な状態の変化は実装時に決定する。
- 関数で書けるものはコンポーネントとして成立するとはかぎらない。UIとして表示するまとまりであるかを考える。
- 設計段階では、実装時の判断までを考慮するのは難しいため、コンポーネントとして候補に挙がる境界線を意識する程度で問題ない。
- コンポーネントはデータを扱うが、保存状況に関わらず状態管理は行われる。セレクトボックスのように状態変化はあるがデータを保存しないこともある。
- 毎回同じ時間設定をするなど、データとして保存されることもある。
- 状態管理の実装方法は、コンポーネント設計の段階では確定できない。状態管理の可能性を優先的に考慮する。
- コンポーネント自身が、どのような役割を持ち状態を変化するのかを決めるため、別Uiとの間にあるデータフローは考えない。
- 必要な責務は、なるべくシンプルに考える。将来の拡張は必要になるまで取り入れず、簡単なもので留めておく。
- 用途が似ているコンポーネントであっても、使う場所や表示方法が異なる場合は共通コンポーネントとして扱わない。

## 型定義

- 型定義はデータ構造を中心に考慮する。この段階では利用する際のデータの動きは考えない。
- どのようなデータが存在するのか、データが持つプロパティや関係性、データをどう分けるのかを考える。
- データ構造が独自のデータではなく、実装時に利用されるものであれば型定義の段階では必要ない。
- 型は単にデータの種類をチェックするものではなく、他のデータとの関係性を表現する。
- 結果的に同じデータであっても、そのデータは何のデータに紐づいているのかを明示する。
- 別のデータ構造から受け取るデータであっても、どんなデータがそこにあるのかを決める。実装時や状態管理のデータの動きはここでは考えない。
- 型で表現できることと、データの意味は必ずしも一致しない。何かしらの処理が挟まる場合は別のデータとして考える。
- API連携などで将来的に独立する可能性があったとしても、最初からファイルを分ける必要はない。現時点での構造を優先し、必要になった段階で分ける方が適切である。
- データ構造をもたないCommonコンポーネントなどは、実装時に汎用的に必要になった場合に限り型定義をする。その都度必要な型定義は型推論の兼ね合いを見ての判断となる。

## テスト

- テストは機能や振る舞いがわかるものを決めていく。
- 具体的な操作や見え方ではなく、宣言的に「何がしたいか」と「何を保証するか」が簡潔にわかるものにする。
- 操作方法ではなく、処理として何が実行できるのかを決める。
- ひとつの処理を、ひとつの宣言で表す。処理の成功とデータの反映は分けなくてもよい。
- 必要な処理をもれなく、また重複することなく宣言する。
- 共通部品のテストと、その部品を利用する機能のテストは重複に関わらず分離しておく。
- 組み込みの機能をそのまま汎用的に使う場合はテストをする価値は低い。独自の処理を持つ場合はテスト対象を検討する。

## テスト実装

- コンポーネントの状態管理はテストに含ませず、データ処理を考える。
- そのデータ処理が「何を実行して何を保証するのか」を決めていく。
- アプリケーション全体を繋げてテストするのではなく、それぞれの責務に絞ってテストする。
- 責務を個別にテストすることで、処理が正しく動作することを部分的に保証する。
- 全体的な構成がどう繋がるかは、コンポーネント設計や実装によって決定される。
